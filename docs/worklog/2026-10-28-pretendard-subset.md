# 본문 폰트를 Pretendard 서브셋으로

**날짜** 2026-10-28
**브랜치** `main`

## 왜 했나

"블로그에 맞는 폰트를 추천해 달라"는 요청에서 시작했는데, 현재 설정을 열어 보니
추천 이전에 **지금 폰트가 동작하지 않고 있었다.**

## 발견한 문제 두 가지

### 1. 한글에는 웹폰트가 아예 안 걸려 있었다

```
public/fonts/ibm-plex-sans-kr-v10-latin-regular.woff2   14.8KB
                                   ^^^^^
```

파일명의 `latin`이 그대로다. 14.8KB로는 한글 글리프가 들어갈 수 없다
(한글 폰트는 보통 1~3MB). 그래서 실제로는 이랬다.

| | |
|---|---|
| 영문·숫자 | IBM Plex Sans KR |
| **한글** | **OS 기본 글꼴** (윈도우 맑은 고딕 / 맥 Apple SD Gothic Neo / 안드로이드 Noto) |

내용의 대부분이 한글인데 고른 폰트가 적용된 적이 없었고, 보는 기기마다 달랐다.

### 2. 굵기가 400 하나뿐이었다 — 라틴만 영향

코드에서 `font-bold`·`font-semibold`·`font-black`을 쓰고, 본문에는 `<strong>`이
글 한 편에만 60개, `h2` 9개, `h3` 6개다.

폰트는 글자마다 따로 정해진다. 그래서 영향은 한쪽에만 갔다.

| 글자 | 어느 폰트로 갔나 | 굵게 |
|---|---|---|
| 한글 | 라틴 서브셋에 글리프 없음 → OS 글꼴 | OS 글꼴에 700이 있어 **진짜** |
| 라틴 | 서브셋에 글리프 있음 → 그 가족 안에서 해결 | 400뿐이라 **가짜** |

처음에는 "`<strong>` 60개가 전부 가짜 굵게"라고 적었는데 틀렸다. 가짜 굵게는
`AI`, `API`, `React` 같은 **라틴에만** 해당했다. 한글 굵게는 멀쩡했다.

그래서 폰트 교체의 실제 이득은 "굵게가 고쳐진다"보다 **한글이 기기마다 다르게
보이던 것이 고정된다** 쪽이 크다.

## 어떻게 골랐나

후보를 실제로 잘라서 재봤다. 블로그가 쓰는 글자만 남겼을 때:

| 폰트 | 굵기 | 원본 | 서브셋 |
|---|---|---:|---:|
| Pretendard Variable | 전부 (변수) | 2.0MB | **201KB** |
| IBM Plex Sans KR | 400/600/700 | 8.1MB | 272KB |
| Noto Serif KR | 전부 (변수) | 22.7MB | 274KB |

셋 다 200~275KB라 **용량은 결정 변수가 아니게 됐다.** 비교 페이지를 만들어
같은 글을 같은 폭(본문과 동일한 720px)으로 나란히 띄워 보고 Pretendard로 정했다.

참고로 서브셋을 하지 않았을 때의 비용(글 한 편 기준 실측):

| 방식 | 용량 | 요청 |
|---|---:|---:|
| Pretendard CDN 동적 서브셋 | 553KB | 22 |
| IBM Plex Sans KR (Google Fonts) | 915KB | 69 |
| Noto Sans KR (Google Fonts) | 1,367KB | 69 |

한글은 음절이 넓게 흩어져 있어 조각이 거의 다 걸린다 — 72개 중 69개.
"필요한 것만 받는다"가 한글에서는 잘 작동하지 않는다.

## 한 일

### `pnpm fonts` — 서브셋 생성

`scripts/gen-fonts.ts`

1. `content/posts/**/*.md` 와 UI 문자열 파일에서 글자를 모은다
2. 라틴·숫자·문장부호(U+0020–024F, U+2000–206F)를 항상 더한다
3. Pretendard Variable 원본(2MB)을 받아 `.next/cache/` 에 두고 재사용
4. 그 글자만 남겨 `public/fonts/pretendard-subset.woff2` 로 쓴다
5. 어떤 글자를 담았는지 `.manifest.json` 에 함께 남긴다

```
원본      2009KB
서브셋     202KB   (90% 줄었다)
글자      1398자  (한글 683자 / 한글 전체 11,172자의 6.1%)
```

### 깜빡해도 조용히 넘어가지 않게

새 글에 없던 글자를 쓰고 `pnpm fonts`를 안 돌리면 그 글자만 시스템 폰트로
빠진다. 비슷한 고딕으로 대체돼서 화면으로는 알기 어렵고 빌드도 통과한다.

`app/lib/fonts/subset.test.ts` 가 본문 글자와 매니페스트를 대조해 실패시킨다.
테스트 3개 추가 (107 → 110).

> 글에 새 글자를 쓰면 `pnpm fonts`를 다시 돌린다. 안 돌리면 테스트가 막는다.

### 적용

`app/utils/fonts.ts` — `weight: "100 900"` (변수 폰트라 파일 하나가 전 굵기 담당),
한글 OS 기본 글꼴을 포함한 fallback 스택 추가. 옛 라틴 서브셋 파일 삭제.

### 겸사겸사

`components/Article/ArticleContent.tsx` 의 `font-body` 클래스를 제거했다.
`tailwind.config.js` 에도 `globals.css` 에도 정의가 없는 죽은 클래스였다.

## 검증

| 항목 | 결과 |
|---|---|
| `npx tsc --noEmit` | 0 |
| `pnpm test` | 110 / 110 |
| `pnpm build` | 85페이지 |
| 산출물 폰트 | 202KB, `rel="preload"` 적용 |
| `@font-face` | `font-weight: 100 900` 확인 |

**폰트 파일에 한글이 실제로 들어 있는지는 매니페스트를 믿지 않고 따로 확인했다.**
생성된 서브셋을 다시 잘라 보는 방법이다 — 글리프가 있으면 글자 수에 비례해
커지고, 없으면 최소 크기에 머문다.

```
한글 (글에 있는 말)    3000B    ← 있다
라틴                  3752B    ← 있다
숫자·기호            11412B    ← 있다
한자 (쓴 적 없음)       744B    ← 없다 (의도대로)
```

## 바뀐 수치

| | 이전 | 이후 |
|---|---:|---:|
| 폰트 파일 | 14.8KB | 202KB |
| 한글 | 웹폰트 없음 | 적용됨 |
| 굵기 | 400만 (나머지는 가짜 굵게) | 100~900 전부 |

**다운로드는 187KB 늘었다.** 폰트가 실제로 동작하게 된 대가다. 대안들(553KB /
915KB / 1,367KB)과 비교하면 가장 가볍다.

## 본문 크기와 행간 — `prose-lg`

폰트 교체와 크기·행간 조정 중 무엇이 더 크게 작용하는지 2×2로 비교해 보고
크기·행간도 같이 올렸다.

임의의 숫자를 정하지 않고 `@tailwindcss/typography`가 제공하는 표준 단계를 쓴다.

| | 크기 | 행간 |
|---|---|---|
| `prose-base` | 16px | 1.75 |
| **`prose-lg`** | **18px** | **1.778** |
| `prose-xl` | 20px | 1.80 |

`app/(ko)/[slug]/layout.tsx` 와 `app/(en)/en/[slug]/layout.tsx` 의
`prose dark:prose-invert` 에 `prose-lg` 를 더했다. 본문뿐 아니라 제목·코드·여백이
같은 비율로 올라간다. 산출 CSS에서 `1.125rem / 1.77778` 확인.

## 아직 안 한 것

### 빌드에 자동으로 끼울지

지금은 `pnpm fonts` 를 손으로 돌린다. 테스트가 누락을 잡아 주므로 사고는 안 나지만,
`prebuild` 에 걸면 그 단계도 없앨 수 있다. 다만 빌드가 네트워크(jsDelivr)에
의존하게 되므로 보류했다 — 현재 빌드는 네트워크 없이 돈다.
