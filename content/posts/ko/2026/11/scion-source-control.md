# Anthropic의 Scion — 인간 규모에서 에이전트 규모로

---

2026년 10월, Anthropic이 자체 버전 관리 시스템 Scion으로 사내 모노레포를 git에서 완전히 옮겼다는 글을 올렸다. 마이그레이션에 걸린 시간은 5개월, 만든 사람은 7명이다.

이유가 흥미롭다. 코드 생산량이 급증하면서 변경을 저장하고 검증하고 병합하는 인프라가 병목이 됐다.

이 사례에서 주목할 것은 처리량뿐 아니라 작업 환경의 변화다. Git의 분산형 설계는 개발자가 독립적인 작업 공간을 유지하는 환경에 잘 맞는다. 반면 Anthropic의 에이전트와 CI 잡은 상시 연결된 인프라에서 대규모로 실행된다.

**작업 환경이 달라지면 기존 설계의 비용과 이점도 달라진다.** Scion은 이 변화가 저장소뿐 아니라 머지 큐와 CI에 어떤 영향을 미치는지 보여준다.

## 1. 숫자가 먼저다

Anthropic 모노레포에 **하루에 병합되는 변경 수**다.

| 시점 | 하루 병합 수 |
|---|---|
| 2026년 5월 | 약 2,500건 |
| 2026년 9월 | 30,000건 이상 |

넉 달 만에 12배 이상 증가했다. Anthropic은 그 배경으로 에이전트를 활용한 코드 생산량의 증가를 설명한다.

에이전트의 병렬 실행은 작업량을 빠르게 증폭시킬 수 있다. 기존 인프라의 처리 용량이 이러한 증가를 따라갈 수 있는지가 문제가 된다.

## 2. git이 버티지 못한 지점

글이 밝힌 저장소 규모다.

- main 브랜치의 히스토리만 약 100 GB
- 압축된 작업 사본이 25 GB 이상
- CI를 위한 체크아웃이 하루 약 2,500만 회

마지막 숫자가 문제다. 25 GB짜리를 하루 2,500만 번 그대로 받으면

> 하루 600 PB 이상의 Git 트래픽

이 된다. 그래서 캐시를 쌓는다. Anthropic은 피크에 **사내 Git 미러를 수백 대** 돌렸다고 한다.

그런데 미러를 늘리면 다른 게 깨진다. 글이 지적한 두 가지가 이렇다.

1. 미러의 **시드가 main의 최신 지점에서 점점 밀린다**(drift). 캐시가 오래될수록 받아야 할 양이 다시 늘어난다
2. 부분 클론(partial clone) 위에서 **`diff`와 `blame`을 계속 동작하게 만드는 게 어려워진다**

미러는 다운로드 부하를 줄였지만, 최신 상태와의 차이 및 부분 클론의 질의 처리 문제까지 근본적으로 해결하지는 못했다.

## 3. 전제를 바꿨다 — "클라이언트는 항상 온라인이다"

Scion의 설계는 git의 **가정 하나**를 뒤집는 데서 시작한다.

Git은 중앙 서버에 의존하지 않고 로컬에서 버전 관리 작업을 수행할 수 있도록 설계됐다. 일반적인 클론은 커밋 이력과 관련 객체를 복제하므로 비행기 안에서도 커밋하고 `log`를 조회할 수 있다. 2005년 Git은 이러한 독립성을 빠른 연산과 결합했다. 분산 버전 관리 자체가 최초였던 것은 아니며, 오늘날에는 shallow clone과 partial clone도 지원한다.

그런데 Anthropic 모노레포의 클라이언트는 대부분 **사람이 아니라 에이전트와 CI 잡**이다. 이들은 데이터센터에서 실행되므로 상시 연결을 설계 전제로 삼을 수 있다.

전제를 바꾸면 따라오는 게 많다.

| | Git | Scion |
|---|---|---|
| 클라이언트 | 기본적으로 이력과 객체를 로컬에 복제 | 항상 온라인, 필요한 것만 요청 |
| 히스토리·blame·머지·리베이스 | 주로 로컬에서 계산 | 서버에서 계산 |
| 커밋 | 로컬에 쌓고 push | 서버에서 생성, push가 없다 |
| 커밋 비용 | 변경량 및 인덱스·트리 처리 비용에 영향받음 | 변경 크기에 비례 |
| 체크아웃 | 파일 작업에 사용, 질의에는 불필요할 수 있음 | 선택, 희소(sparse)·가상 체크아웃 |
| 조회 | 로컬 CLI 또는 플랫폼 API | API로 노출 |
| 저장소 유지보수 | packfile 정리 등 필요 | packfile 자체가 없음 |

"소스 컨트롤을 API로 노출한다"는 항목이 실용적으로 제일 크다. 많은 CI 잡이 로컬 저장소 없이 질의만으로 일을 끝낸다. 자동 bisect와 자동 revert 파이프라인이 이것 위에 올라가 있다.

## 4. 데이터 모델 — 트리가 아니라 변경 목록

Git의 커밋은 해당 시점의 루트 트리를 가리킨다. 논리적으로는 스냅샷이지만 매번 모든 파일을 복제하는 것은 아니다. 변경되지 않은 트리와 blob 객체는 재사용한다.

Scion의 단위는 changeset이고, 이건 선행 기록 로그(write-ahead log)의 한 항목이다. 가리키는 게 다르다.

```text
Git commit   →  그 시점 트리 전체를 가리킨다
changeset    →  첫 번째 부모 대비 "바뀐 파일 목록"만 담는다
                (내용은 압축된 blob에 대한 content-addressed 포인터)
```

ref 갱신은 changeset 생성과 분리돼 있다. Spanner의 행 하나에 대한 compare-and-swap으로 처리한다. 커밋 객체 생성과 ref 갱신을 별도로 처리하는 구조다. 동일한 ref에 대한 경쟁은 여전히 조정해야 한다. 글이 "값싸고, 증분이고, 잠금이 없는 커밋"이라고 부르는 게 이 구조다.

대신 대가가 있다. changeset이 변경분만 들고 있으면, `blame`이나 파일 히스토리처럼 과거 전체를 훑어야 하는 질의가 비싸진다.

그래서 Scion은 그걸 <strong>파생 데이터(derived data)</strong>로 따로 만든다.

- blame 구조, 경로 히스토리 구조, 커밋 그래프용 skip list
- 각 파생 타입은 부모의 값에서 재귀적으로 계산된다
- 타입을 추가할 수 있고, 즉시 계산할지 지연 계산할지 고를 수 있고, 클라이언트를 바꾸지 않고 최적화할 수 있다

이게 설계의 핵심이라고 본다. 일반적인 Git의 `blame`은 로컬 이력을 분석하는 연산이다. Scion은 서버에서 파생 데이터를 계산하고 재사용해 질의 시점의 반복 연산을 줄인다. 파생 데이터는 즉시 또는 지연 계산할 수 있다.

## 5. 3계층, 그리고 전송 프로토콜

`scn` 클라이언트가 git과 다른 지점은 <strong>협상(negotiation)</strong>이다.

git의 fetch는 "내가 뭘 가지고 있는지"를 서버와 주고받은 뒤, 서버가 그 차이를 packfile 하나로 말아서 보낸다. Scion은 그걸 하지 않는다.

```text
1. 클라이언트가 "원하는" 트리와 blob 만 협상한다 (가진 것은 따지지 않는다)
2. 없는 트리를 재귀적으로 받아 온다
3. 그 다음 blob 을 받아 온다
```

요청 하나하나가 **불변(immutable) 객체**에 대한 요청이다. 이 구조는 두 가지 이점을 제공한다.

- 해당 객체를 보유한 캐시가 응답할 수 있다. 서버가 매번 계산할 필요가 없다
- 중단된 전송을 이어받을 수 있다. 거대한 packfile을 처음부터 다시 받지 않는다

구조는 세 계층이고, 셋 다 같은 RPC를 쓴다.

| 계층 | 위치 | 역할 |
|---|---|---|
| `scion-daemon` | 노드마다 하나 | 클라이언트와 소켓으로 연결 |
| `scion-cache` | 리전 단위 | 메모리에서 객체를 스트리밍 |
| `scion-server` | 권위 | Spanner / 클라우드 스토리지에서 읽음 |

계층을 엄격하게 나눈 중요한 이유는 장애 격리다. 특정 계층의 장애가 다른 계층의 과부하로 이어질 위험을 줄이기 위한 설계다.

## 6. 결과

글이 보고한 수치다.

| 항목 | 결과 |
|---|---|
| 각 계층의 캐시 적중률 | 99% 이상 |
| 인프라 CPU·메모리 규모 | 기존 Git 미러 대비 약 1/200 수준 |
| CI·연구 잡의 체크아웃 | 분 단위 → 초 단위 (약 2자릿수 개선) |
| CI의 CPU 여유 | 25% 확보 |
| 장기 상태(long-lived state) | 서비스·캐시 노드에 종속된 장기 상태 없음 |

영속 데이터는 Spanner와 클라우드 스토리지에 보관한다. 서비스 및 캐시 노드에 종속된 장기 상태가 없으므로 개별 노드를 교체하거나 확장하기 쉽다.

## 7. 머지 큐와 CI의 의미가 달라진다

구현보다 이 대목이 더 오래 남았다.

Anthropic은 에이전트 규모에서 엄격한 머지 큐의 실효성이 낮아진다고 설명한다.

머지 큐는 변경의 병합 순서와 통합 상태의 검증을 조정한다. 예상 병합 상태를 병렬로 테스트하거나 여러 변경을 묶는 방식도 가능하다. 다만 Anthropic은 자신들의 변경 규모에서 전역적인 사전 병합 검증이 처리량을 제한한다고 판단했다.

글은 더 날카로운 질문을 던진다.

테스트가 도는 동안 수백, 수천 건이 병합될 수 있다면 CI는 무엇을 보장하는가?

테스트 결과는 검증한 커밋에 대해서는 여전히 유효하다. 다만 테스트가 끝날 때의 최신 main까지 검증됐다는 뜻은 아니다.

그래서 Anthropic은 전역 잠금을 재현하는 대신 병합 후(post-merge)·배포 전(pre-deploy) 자동 테스트에 투자했다. 동시 변경이 서로 충돌하는 건 받아들인다. 근거는 이것이다.

Anthropic은 이러한 충돌을 Claude가 빠르게 수정할 수 있었다고 설명한다.

사전 검증에 집중하던 전략을 병합 후 회귀 탐지와 복구에도 배분한 것이다. 이 선택은 회귀를 빠르게 탐지하고 수정할 수 있다는 조건에 의존한다. 보안이나 데이터 무결성처럼 사후 복구가 어려운 변경에 동일한 전략이 적합하다는 뜻은 아니다.

## 8. 사람은 무엇을 했나

글에서 가장 많이 인용될 문장은 아마 이것이다.

원문에 따르면 이 시스템을 만든 엔지니어들은 Claude의 코드 작성 능력을 높게 평가했다.

그럼 사람은 뭘 했나. 글의 답은 이렇다.

- 시스템 전체에 대한 이해와 설계 수준의 트레이드오프 판단
- 그리고 — "엔지니어의 역할은 Claude에게 '아니'라고 말하는 것이었다."

에이전트가 때때로 시스템의 핵심 제약을 위반하기 때문이다. 동작하는 코드를 쓰는 것과 이 시스템이 지켜야 하는 선을 지키는 것은 다른 일이고, 뒤쪽이 사람 몫으로 남았다는 이야기다.

리뷰 방식도 바뀌었다. 원문은 사람 리뷰어가 변경의 의도에 더 집중하는 방향을 설명한다. 모든 코드 수준의 검증이 불필요해졌다는 의미로 확대할 수는 없다.

한 가지 구체적인 사례가 있다. Git → Scion 수집(ingestion) 프로토타입을 Claude에게 다시 쓰게 했더니, 메모리를 20배 덜 쓰고 4배 빠른 버전이 나왔다고 한다. 그리고 개별 컴포넌트를 감시하는 "슈퍼팬(superfan)" 에이전트를 따로 둔다고 한다.

## 9. Git은 사라질까

Anthropic은 Scion이 범용 Git 대체재가 아니라고 명시한다.

Scion은 상시 연결된 클라이언트, 거대한 모노레포, 높은 동시 변경량에서 특히 가치가 크다. Spanner는 이러한 설계를 구현하기 위해 선택한 기술이지 필수 조건은 아니다. 에이전트가 아닌 인간 개발자 중심의 조직에서도 비슷한 규모의 문제는 발생할 수 있다.

Google의 Piper와 Meta의 Sapling(특히 Mononoke와 Bonsai 데이터 모델)이 선행 사례다. Anthropic은 이미 대규모 모노레포에서 검토해 온 방향을 에이전트 중심의 환경에 적용했다.

Git의 기본 개념인 커밋, ref, blame, diff는 Scion에서도 이어진다. 달라진 것은 주로 데이터 모델과 연산 위치, 전송 방식이다.

Git 역시 다음과 같은 최적화를 지원한다.

| Git 기능 | 하는 일 |
|---|---|
| partial clone | 일부 객체의 다운로드를 지연한다 |
| sparse checkout | 작업 트리의 일부 경로만 펼친다 |
| commit-graph | 커밋 그래프 탐색에 필요한 정보를 저장한다 |

일부 최적화 방향은 Scion과 유사하다. 다만 Git은 기존 호환성과 분산형 작업 모델을 유지해야 한다. packfile도 오프라인 작업만을 위한 장치가 아니다. 객체 압축과 효율적인 네트워크 전송에 가치가 있다.

Anthropic이 제안하는 방향 역시 Git 자체의 폐기보다는 새로운 서버 아키텍처와 서버 사이드 RPC를 Git 생태계에 적용하는 것이다. 기존 도구와의 호환성, 운영 비용까지 고려하면 일반적인 팀에서는 Git을 유지할 이유가 충분하다.

## 10. 숫자를 읽을 때

이 글의 성능 수치는 모두 Anthropic의 자체 보고치다. 독립적인 벤치마크는 아니다.

인프라 규모가 약 1/200 수준으로 줄었다는 결과는 자신들이 운영하던 기존 Git 미러 인프라와 비교한 값이다. 다른 최적화된 Git 서버와 동일한 조건에서 비교한 결과로 해석해서는 안 된다.

그럼에도 하루 30,000건 이상의 병합과 약 2,500만 회의 체크아웃은 아키텍처를 재검토할 만한 규모다. 수치 자체보다 그 부하에 대응하기 위해 어떤 설계 결정을 내렸는지가 중요하다.

## 정리

코드 생산 비용이 내려가면 이전에는 크게 드러나지 않았던 체크아웃, 리뷰, 통합 검증 등의 비용이 새로운 병목으로 등장할 수 있다.

개발 인프라를 설계할 때는 두 가지 조건을 함께 고려해야 한다. 작업 주체가 얼마나 많은 변경을 생산하는가, 그리고 어떤 환경에서 작업하는가.

처리량의 변화는 기존 시스템의 확장으로 대응할 수 있는 경우도 있다. 그러나 작업 환경까지 달라진다면 기존 설계의 비용과 이점을 다시 평가해야 한다.

Scion을 도입하지 않는 팀에도 남는 질문이 있다. 현재의 코드 리뷰와 CI 전략은 증가하는 변경량을 감당할 수 있는가? 검증 비용을 줄이면서도 시스템의 핵심 제약을 유지할 수 있는가?

Scion이 흥미로운 이유는 Git보다 빠르다는 자체 보고 수치뿐 아니라, 기존 설계의 전제를 재검토하고 그에 맞춰 아키텍처와 워크플로를 바꾼 구체적인 사례라는 점에 있다.
